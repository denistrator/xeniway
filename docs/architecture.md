# Architecture

## Runtime

The browser runs a React/Vite single-page application. In development, Vite proxies `/api` to the Bun/Elysia server. The API owns authentication, authorization, validation, and persistence. PostgreSQL is the source of truth for users, sessions, applications, and password-reset tokens. Redis is a supporting dependency used only to rate-limit login, registration, and password-reset requests. SMTP is an outbound delivery dependency behind an injectable mailer interface.

The product boundary is a private candidate workspace for employer conversations, application progress, follow-ups, and outcomes. The shared workflow has exactly six statuses—`saved`, `applied`, `interview`, `offer`, `rejected`, and `withdrawn`. Archive and blacklist remain separate lifecycle states, not status values. Each application detail view combines the application with a newest-first activity timeline.

```text
React + React Router
        │
        ├── Redux Toolkit: filters, drawer, theme
        └── TanStack Query: authenticated server data and mutations
                │ fetch with credentials + CSRF header
                ▼
        Bun + Elysia + Zod
                │
        AuthService + typed repositories ──→ Drizzle ORM → PostgreSQL
                │
        Redis rate limiter (auth + password reset)
```

## Workspace boundaries

### Read-only offline access

Native PWA installation metadata lives in `apps/web/pwa-manifest.ts`. The existing Vite PWA plugin generates and links `/manifest.webmanifest` in the production HTML, with stable `/` identity/start URL/scope and standalone display. Public app icons include 192/512px PNGs, a separate opaque mask-safe 512px variant, and a 180px Apple touch icon. Installation does not register the worker or authorize private offline downloads: automatic registration remains disabled, and explicit preparation downloads the public manifest/icons along with the shell. The worker accepts only their exact paths and JSON manifest MIME types; SHA-256 revisions cover these unversioned assets too. No custom install prompt is implemented.

`features/offline` separates verified server sessions from cached-device access. Explicit browser-profile consent downloads all three application lists, every unique workspace in those lists, and public build assets. Workspace responses include application fields, activity, preparation, contacts and follow-up tasks. Details use existing owner-scoped endpoints and query keys with at most four concurrent preload requests. Versioned IndexedDB records hold one account's ID/email, readiness and seven-day expiry, and allowlisted application responses. Auth/CSRF queries, credentials, preferences, and mutations are never persisted. Cached identity never enters `auth/me`. Query keys include the read owner; mutation invocation variables capture ownership so late A responses cannot populate B's cache.

Access lifecycle policy lives in the pure `offline-access-machine.ts`: separate typed connection, session and download states derive read ownership and remote permissions. `offline-access-runtime.ts` owns query observation, browser/channel subscriptions, storage operations and timers for one mounted provider. It applies policy synchronously and exposes stable snapshots through the thin `OfflineAccessProvider`. Controls keep only owner-scoped consent and the query-derived response timestamp; preparation progress, failure and worker-update notices come from the runtime. Named actions distinguish download removal, local sign-out, preparation and reconnect verification.

Verification and preparation carry operation identities; restoration and mounted subscriptions carry invalidation generations. Obsolete completions cannot reopen access or restore a removed download. Ordinary auth-cache observations update identity without recovering an unavailable connection; matching completed reconnect verification or an explicit successful login/register restores remote permissions. Reconnect cancels any older session check before fetching fresh proof; successful authentication cancels pre-sign-in checks before installing its response. Transient `auth/me` failures also disable remote access while preserving eligible local reads. Auth policy is observed synchronously to prevent queued rejection/success notifications from overwriting newer sessions. Rejected restoration, including invalidated restoration after an account switch, clears only its captured durable download generation. Query-originated React notifications remain scheduled; browser connection-loss events notify immediately so open editors become read-only in the same event.

Preparation replacement notifications use the mounted runtime channel, which does not receive its own messages. Standalone preparation retains its own notification sender. Notification failures are inside captured-generation cleanup. Disposal exits pending verification/preparation states, closes and releases the channel, and invalidates completion handlers; a restarted runtime can begin a new operation without promoting old work.

Each explicit preparation has a private random generation marker in the existing account store. Preparation assertions, snapshot writes, readiness and failure cleanup compare that marker transactionally so a superseded same-owner run cannot complete or clear a newer download. Ready/restored metadata carries this internal marker to guard automatic persistence and expiry cleanup too; legacy metadata explicitly expects no marker. A replacement broadcast invalidates the old tab's saved account even for the same owner, preserving online access but stopping its old persistence/timer. Superseded persistence is a benign skipped write, not a storage-permission error. Automatic expiry never performs profile-wide removal or broadcasts a broad removal; explicit user removal/logout retain their broader cleanup. New preparation readiness requires the public build, all three lists and a durable detail response for every listed ID; older list-plus-visited snapshots remain readable until explicitly refreshed. Successful preparation returns its ready metadata from the final transaction rather than opening another snapshot reader. Current-owner detail cache entries absent from the refreshed lists are pruned before persistence. Progress counts completed unique workspaces, not assets. Refresh is a verified-online explicit action that replaces private stored data, removes displayed readiness during download, and starts a new seven-day period; failed runs leave no ready private download. No point-in-time server-wide snapshot is promised across separate HTTP requests.

The custom production worker caches public assets only after preparation, never API responses or token-bearing navigation URLs. Partial downloads cannot mark readiness. Transactions reject expired, disabled, or superseded owners. Transport failures preserve downloaded reads; confirmed authorization failures and account changes clear private offline records. Reconnect verifies the session before refreshing reads or enabling edits. Mutations fail immediately offline, without persistence or replay. Offline creation, local drafts, and background synchronization are not implemented.

Offline restoration runs alongside the initial render with a two-second bound, without blocking ordinary online layout rendering. A late restore cannot override verified identity, logout, removal, or a cross-tab account replacement. Read-only routes wait for eligible restoration when needed. The displayed download timestamp comes from the current list/detail query, separately from the seven-day preparation expiry. The lazy-route suspense boundary sits inside the persistent main element so keyboard skip-link focus survives page loading.

Production snapshot readers evaluate their validation clock after the transaction reads the relevant records, not before asynchronous database opening. This permits a valid concurrent save to precede the read without being mistaken for a future snapshot; explicitly supplied clocks remain available for deterministic expiry and corruption tests. Local and cross-tab logout cancel outstanding `auth/me` queries before clearing identity, so a pre-logout response cannot restore authenticated access.

A transient private-API failure also preserves the requested route and existing in-memory query data for a session already verified in the current tab, even without an offline download. This does not persist data or enable a cold offline launch. Writes and remote reads remain blocked until Retry/reconnect verifies `auth/me`; a successful new sign-in also restores the write guard. Confirmed authorization failures still clear private access, and explicit local/cross-tab removal revokes cached-device fallback until fresh session verification. Read-only workspace controls prevent entering editors, while already-open editors retain cancellation and confirmation dialogs retain No/backdrop/Escape dismissal. Save and destructive confirmation stay disabled, without disabling the entire workspace subtree.

Auth-cache, runtime snapshots and download-timestamp subscriptions use `useSyncExternalStore`. TanStack Query-originated notifications use scheduled `notifyManager.batchCalls` delivery: query construction can emit cache events during another component's render, so custom subscribers must not synchronously force React updates from those events. Preference application remains in the existing post-commit effect, without hydration gates or automatic uploads.

Downloaded access is not authentication or encrypted device protection: anyone using the browser profile may read it within seven days, remote revocation cannot be detected without reconnecting, and browser eviction may remove it earlier. Offline logout clears private local records but cannot revoke the remote server session.

### Frontend styling

Tailwind CSS v4 generates utilities through the Vite plugin. Tailwind Variants owns variant recipes and class conflict resolution; `apps/web/src/lib/utils.ts` wraps its `cn()` to preserve the application's definite-string return contract. The web package has no direct CVA, clsx, or tailwind-merge dependency.

Define component recipes at module scope in colocated `foo.styles.ts` files. Every native HTML element has its own semantic slot, including unstyled elements; repeated instances of one mapped element share that slot. Use variants when an existing UI state changes styling. Button keeps its `variant`, `size`, `asChild`, native props, and forwarded ref; Card retains independent React components backed by slot functions. Pass caller classes to the relevant slot with `className`, so overrides are merged once. Use `VariantProps` for inferred public variant props and `cn()` inside styling modules when composing shared recipes. Keep complete literal class names for Tailwind discovery; no literal Tailwind classes belong in production TSX.

Shared `components/ui/field-styles.ts` and `surface-styles.ts` recipes cover validation, textarea/label styling, empty states, editor forms, dialog backdrops, and collection actions. Feature-local recipes cover navigation selection, search decoration, all six status colors, activity forms/events, follow-up completion, authentication feedback, and workspace editing feedback. `board/job-status-styles.ts` separates status decoration from canonical status ordering and translated labels.

Use the same component basename for colocated files: `foo.ts` owns logic, `foo.tsx` owns rendering, `foo.styles.ts` owns Tailwind Variants recipes, and `foo.test.tsx` owns component behavior tests. For example, `application-activity-form.ts` exports `useApplicationActivityForm`, and `application-activity-form.tsx` exports `ApplicationActivityForm`. Logic filenames do not use a `use-` prefix; React hooks still require a `use` function prefix. Apply this convention to new and refactored components without renaming unrelated existing modules. Tests cover behavior and accessibility, not styling.

Imports explicitly select `.tsx` for rendering and `.ts` for logic when both share a basename. The web app enables `allowImportingTsExtensions` with its no-emit compiler setup and uses non-composite typechecking. TypeScript's glob discovery prioritizes `.ts` over same-basename `.tsx`, but explicit rendering imports bring those files into the checked dependency graph without a manual component list. The browser entry `src/main.tsx` is explicitly registered in `tsconfig.app.json`'s `files` because Vite loads it through HTML, which TypeScript does not follow. Keep other rendering files reachable through component or behavioral-test imports; an unreferenced paired `.tsx` file is not discovered automatically.

The root `tsconfig.json` supplies shared compiler defaults, not a project-reference build graph. The web's default `tsconfig.json` extends the browser configuration for editor use. Its `typecheck` script runs separate `tsc -p` checks for `tsconfig.app.json`, `tsconfig.node.json`, and `tsconfig.offline-worker.json`, preserving browser, Node, and worker environment boundaries. Browser and Node checks retain incremental caches under `node_modules/.tmp`; `build` runs the same typecheck script before Vite bundles the app. Root verification checks shared, API, web, and E2E projects explicitly rather than relying on `tsc -b` orchestration.

The frontend uses a rendering-only TSX boundary. Matching `.ts` files own event handlers, state/effects, query feedback, translations, date formatting, sorting, and edit/confirmation decisions; shared contracts and focused support hooks retain their existing `.ts` homes. TSX wires these hooks/helpers and retains rendering conditions, list mapping, slot bindings, ref forwarding, and JSX-only render callbacks for third-party controls. Behavioral adapters for those callbacks belong in `.ts`, not inline JSX handlers. Static components do not need empty logic modules. State-independent slot sets are initialized at module scope. Preserve lazy route/create-form boundaries and do not replace rendering with `createElement` in a logic file merely to avoid TSX.

Grow recipes when component behavior introduces a real styling distinction. Use slots when several elements respond to the same state, and use compound variants when a particular combination of existing variants needs additional classes. Keep independent variants independent; do not enumerate combinations without a styling requirement. Keep static layout classes in the owning slot recipe. Put base classes in the recipe before variant classes, and reserve slot `className` arguments for caller overrides: a broad caller override can intentionally replace a more specific variant class.

CSS remains responsible for theme tokens and dark-mode selection in `index.css`, floating-label child/peer selectors in `components/ui/floating-label.css`, board scroll behavior, reduced motion, and Atlaskit's accessible edit targets in `workspace-inline-edit.css`. Preserve those DOM class hooks when refactoring. Styling variants consume existing UI state; Redux, TanStack Query, i18next, form hooks, and native/ARIA attributes continue owning behavior and semantics.

`packages/shared` is the contract boundary. It defines the six-status enum, registration/login schemas, application and manual-event input schemas, and public response types. The web and API packages import these definitions instead of duplicating validation or JSON shapes.

`apps/api/src/app.ts` is an injectable Elysia app factory. It owns dependency construction, global middleware, and error handling, then mounts the domain composition in `apps/api/src/routes/index.ts`. Health, auth, preferences, and application endpoints live in their own routers; application routes are grouped by collection, item, event, and board responsibilities. Shared request guards and cookie/response helpers live under `apps/api/src/routes/support/`. Typed repository dependencies allow route behavior to be tested with in-memory implementations. `apps/api/src/server.ts` wires the production Drizzle repositories, Redis rate limiter, and independent database/Redis health checks.

`apps/web/src/lib/api.ts` provides the typed HTTP client. `apps/web/src/lib/queries.ts` owns TanStack Query keys, authentication queries, CSRF acquisition, mutations, and cache invalidation. TanStack Query owns the server preference record; Redux contains immediate presentation state such as the active theme and welcome dialog.

Application workspaces use `@atlaskit/inline-edit` for compact and multiline fields. Status uses a separate dropdown whose options save immediately. Field hooks validate and persist only the changed value through the existing owner-scoped update API. A dirty compact field asks whether to save or discard before leaving. The application form remains create-only and retains its modal/drawer presentation preference.

The shared layout mounts a lightweight `CreateApplicationLoader`, not the create form itself. It checks authentication outside the lazy import and starts loading `JobManagerHost` only when Redux's create-dialog open flag first becomes true for the current account (the Add job action, including keyboard activation). There is no hover/focus preload. A localized screen-reader status announces loading. The header captures the activation-time Add job element in a React ref before dispatching the open action; that ref reaches the existing dialog focus hook without storing DOM elements in Redux. The hook snapshots the connected opener on each open, so focus returns to Add job even if the user tabs elsewhere during the first download. After first use, the host remains mounted across close/reopen and route navigation so pending mutations and errors retain their existing lifetime. The account-keyed boundary unmounts on logout/authentication loss and resets on account changes. This retains the host, not closed-dialog form drafts: the existing closed modal/drawer still unmounts its form content. See the [bundle-cost measurements](frontend-bundle-cost.md) for complete-route effects.

The workspace page owns the detail query and passes its data to a small content composition. Overview, lifecycle, preparation, contacts, and follow-ups live in focused domain directories; each domain owns its editing state and mutations. Shared helpers cover text editing, URL safety, and mutation feedback without introducing a generic workspace controller. The sibling activity feature provides a query-backed collection view and a controlled workspace section that uses the supplied events without fetching them again.

The overview places company, position, and status alongside lifecycle actions, followed by a full-width metadata row for location, salary, applied date, and job listing. Below it, workspace sections and activity use a responsive two-column layout. Activity always sorts newest first by occurrence timestamp, then descending event ID for ties, without mutating the supplied array. Sorting-direction selection is deferred to the backlog; memoizing this small sort is not an architectural requirement.

The company/position/status block uses the shared status recipe's `workspaceHeading` slot: a four-pixel inline-start rail and a matching low-opacity gradient that fades toward the inline end. All six hues match the board and status marker, with light/dark variants and reversed gradient direction for Hebrew RTL. Decoration follows the saved application status, not archive/blacklist state. Lifecycle actions, metadata text, validation, and focus colors remain independent; the heading does not clip inline-edit controls or the status popup.

The recipe's `workspace` slot also supplies a scoped `--workspace-status-color` for the metadata panel's two-pixel top edge, short decorative lines before top-level section titles, and a faint activity-panel border blended with the neutral theme line color. About/application notes share the detail-title treatment; preparation subfields and user-entered contact, task, and event titles stay neutral. Logical dimensions and margins mirror title accents in RTL. The selectors in `workspace-status-decor.css` apply only inside the workspace; collection activity keeps its original layout and decoration. No extra status state or mutation behavior is introduced.

The user-preferences repository and API store account-scoped `selectedLanguage`, `selectedTheme`, `selectedFormPresentation`, and `wasIntroduced` values separately from the `users` record. Selected values are nullable until explicitly chosen. The browser applies its flat `userPreferences` local-storage object (`language`, `theme`, `formPresentation`, and `wasIntroduced`) immediately. A successful login or registration fetches the account record, applies non-null selected values over the cache, and always applies server `wasIntroduced`; it never uploads browser defaults. Explicit user actions update local storage and the UI before sending best-effort authenticated writes. A successful login or registration creates an explicit frontend welcome trigger; the layout then reads preferences and renders the welcome dialog only when the account has not been introduced.

The UI follows an accessibility-first baseline: semantic controls and labels, keyboard-operable workflows including a keyboard alternative to drag-and-drop, visible focus indicators, managed focus within dialogs and drawers, live regions for asynchronous feedback, responsive layouts, and reduced-motion support. The document theme is initialized before React starts to avoid a flash of the wrong theme.

The shared header exposes a localized login link after the current-user session resolves as signed out. The link is absent during session loading and for authenticated users, whose account and workspace controls remain unchanged.

The UI language is owned by i18next/react-i18next. English is initialized before the first React render; Russian, Ukrainian, and Hebrew resources are dynamically imported before switching. Hebrew sets the document direction to right-to-left, while the other locales use left-to-right. The language selector persists the selected value in the flat `userPreferences` browser object and synchronizes it with the authenticated account. Theme, language, and job-form presentation share that key with the cached `wasIntroduced` value. Redux does not duplicate locale state, and local storage is never treated as account identity or authoritative onboarding state.

## Request lifecycle

1. The browser acquires a CSRF token from `GET /api/auth/csrf`; the server creates an anonymous session when needed.
2. Registration or login validates the shared schema, replaces the anonymous session, and sets an authenticated HttpOnly session cookie.
3. `GET /api/auth/me` restores the current user on page load. All consumers share the `auth/me` query: successful results remain fresh for one minute, and failed checks do not retry just because another consumer mounts (including lazy-route and StrictMode remounts). Stale results still revalidate on mount, window focus, or reconnect; unsuccessful checks can recover on focus/reconnect or explicit refetch. Login/registration/logout update the shared cache immediately, and application authorization failures still clear account caches. A full page reload starts a new session check; this browser cache never replaces server-side authentication or ownership checks.
4. Application reads require a valid session and are filtered by `userId` in the repository.
5. Application mutations require both a valid session and the CSRF token belonging to that session.
6. TanStack Query invalidates application lists and detail data after mutations so the UI reflects the server state. System events are inserted inside the same PostgreSQL transaction as their application mutation; manual event mutations invalidate only the relevant detail query.
7. After authentication, the preferences query applies the current account's non-null language, theme, and job-form presentation values to the UI and browser cache. Explicit preference changes update local storage and the UI first, then use `PATCH /api/user/preferences` with the authenticated session's CSRF token in the background. Account changes clear account-specific preference query state.

Locale-neutral API values are translated only at the presentation boundary. Application statuses and error codes remain canonical, candidate-entered data is never machine-translated, and displayed dates are formatted with the active locale while stored ISO timestamps remain unchanged.

Pre-feature applications have no persisted creation event because schema migrations do not insert application data. The detail route derives a read-only creation marker from their existing creation timestamp; all subsequent system history is persisted transactionally. Archived and blacklisted cards expose an expandable Activity section backed by the same detail query.

Login, registration, and password-reset requests consume an atomic Redis counter with a fifteen-minute fixed window and a limit of five attempts per normalized email. Counter keys contain a SHA-256 digest rather than the raw email. If Redis is unavailable, these flows fail closed with a `503` response instead of bypassing abuse protection.

## Data ownership

Data export downloads a ZIP package containing application, contact, and follow-up CSV files. Each file is owner-scoped; contacts and follow-ups carry the application ID needed to join them to the application rows. Application export uses one ordered field allowlist in `apps/api/src/routes/applications/export-csv.ts`, pairing each column header with its value reader. The same definition generates headers and row cells, including the derived board value, and all cells pass through the spreadsheet-safe serializer.

Applications and activity events are never addressed without an authenticated owner in repository calls. Archive is a state transition represented by `archivedAt`; blacklist is an independent exclusion state represented by `blacklistedAt` and `blacklistReason`. Active, archive, and blacklist lists are separate queries. Blacklisting preserves the six-status workflow and restores the job to its previous active status when removed from the blacklist. Permanent deletion is accepted for any owned application; the UI exposes it from archive and blacklist views, and database cascading deletion removes its activity history.

## Production security boundary

Password recovery obtains the anonymous CSRF session and rate-limits the normalized email. An unknown account and a known account whose token is stored and message is delivered receive the same generic success. Token-storage or mail-delivery failures for a known account return a distinguishable `500` server error. For an existing user PostgreSQL stores only the token hash. SMTP carries the raw token inside the reset link; when SMTP is intentionally absent outside production, the console mailer logs the complete reset URL and raw token. Confirmation consumes an unused, unexpired token, updates the Argon2id password, and removes all sessions for that user.

Production startup requires explicit non-local PostgreSQL, Redis, and SMTP service URLs, a non-local sender, and an explicit HTTPS `APP_ORIGIN`; missing SMTP configuration is rejected, so production cannot select the console mailer. `CORS_ORIGIN` defaults to `APP_ORIGIN` and must also be HTTPS. Session cookies are HttpOnly, SameSite=Lax, and `Secure` in production. CSRF tokens are stored with the session and required for mutations. Redis rate limits login, registration, and password-reset requests with hashed identifiers and fails closed if the limiter is unavailable. Reset tokens are random, expire after one hour, are stored only as SHA-256 hashes, can be used once, and successful resets invalidate all sessions.

## Workspace application navigation

The workspace header provides previous/next icon buttons using the same compact control styling as the language selector. Navigation includes all applications in the current active, archive, or blacklist collection, ignoring board search and status filters. It follows saved, applied, interview, offer, rejected, and withdrawn column order, preserving the collection order inside each column, skipping empty columns, and wrapping in both directions.

Navigation uses the existing owner-scoped collection query and its offline cache; it does not preload workspace details. Controls are disabled when the current application has no neighbor or the collection is unavailable. An offline destination without downloaded details uses the existing unavailable-detail screen. Changing application ID resets workspace editors and focuses the destination heading. Unsaved edits are not automatically saved when leaving a workspace.
