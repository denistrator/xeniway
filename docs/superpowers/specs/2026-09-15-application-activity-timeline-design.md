# Application Activity Timeline

## Goal

Give every application a trustworthy, chronological history of the candidate's job-search activity. The timeline combines system-generated application history with rich, user-created events such as follow-ups, calls, emails, and interviews.

## Scope

The first version is application-specific. It does not introduce shared employer records, contacts, a general journal, email synchronization, calendar synchronization, reminders, notifications, or automatic email parsing.

## Product behavior

Every application has an activity timeline ordered newest-first. An event records what happened and when it happened. The user may enter a past `occurredAt` value; `createdAt` remains the server audit timestamp.

System events are generated by meaningful application mutations:

- application created;
- application edited;
- status changed;
- archived;
- restored from archive;
- blacklisted;
- restored from blacklist.

Permanent deletion removes the application and its events; it does not create a retained event.

User-created events support these types:

- note;
- email sent;
- email received;
- phone call;
- interview scheduled;
- interview completed;
- offer received;
- rejection received;
- follow-up;
- custom.

System events are visually distinct and cannot be edited or deleted. User-created events can be edited and deleted by the owning user. Events cannot be moved between applications.

## Data model

Create an `application_events` table with:

```text
id
user_id
application_id
type
title
description
occurred_at
created_at
updated_at
metadata
```

`user_id` is retained even though applications are user-owned so every event operation has an explicit ownership boundary. `application_id` and `user_id` reference their parent records. Deleting an application cascades to its events.

Create indexes for application timeline reads and future user-level activity views:

```text
(application_id, occurred_at)
(user_id, occurred_at)
```

Event types and metadata are validated through shared Zod schemas. Metadata is type-specific and constrained; it is not an unstructured replacement for application fields.

## API

Use these authenticated routes:

```text
GET    /api/applications/:id
POST   /api/applications/:id/events
PATCH  /api/applications/:id/events/:eventId
DELETE /api/applications/:id/events/:eventId
```

The application detail response includes the timeline:

```json
{
  "data": {
    "application": {},
    "events": []
  }
}
```

Every read and mutation first verifies that the application belongs to the authenticated session user. Mutations require the existing CSRF protection. User-entered titles and descriptions are treated as plain text and rendered safely.

Application mutation and system-event insertion occur in one database transaction. A status change must never succeed while its history event fails to persist.

## Frontend experience

The application drawer and modal each contain an Activity section with:

- newest-first timeline entries;
- event icon and translated type label;
- title, description, and occurred date;
- useful relative-time presentation where appropriate;
- visual distinction between system and user-created events;
- an Add activity action;
- edit and delete actions for user-created events;
- loading, empty, and error states.

The event form supports type, title, optional description, and occurred date/time. It uses semantic labels, accessible names, focus management, keyboard operation, responsive layout, and the existing English/Russian/Ukrainian/Hebrew translation structure. It works in both drawer and modal form presentations.

The first version does not add a follow-up reminder date. The event model must remain extensible so reminders can be added later without changing the meaning of `occurredAt`.

## Query and mutation flow

The existing application-detail query supplies the application and events together. Creating, editing, or deleting an event updates or invalidates that query. Application mutations update the application and create system events in the same server transaction, then refresh the detail view through the existing TanStack Query patterns.

The timeline must not block the rest of the application form while it loads. Errors in the timeline are shown in the Activity section and do not hide the application fields or prevent unrelated application actions.

## Testing

Cover the feature at the appropriate layers:

- shared schema tests for event types, required fields, date parsing, and metadata validation;
- repository tests for event mapping, ordering, ownership, cascade behavior, and transactional system-event creation;
- API tests for authentication, CSRF, ownership isolation, CRUD behavior, and application-detail responses;
- component tests for empty/loading/error states, manual event validation, editing, deletion, and accessible controls;
- E2E coverage for creating an application, observing system events, adding a follow-up, editing/deleting a user event, changing status, and checking the timeline after reload;
- locale coverage for all four dictionaries and date formatting.

## Acceptance criteria

- Every application detail view exposes a reliable chronological activity history.
- Meaningful application mutations produce system events transactionally.
- Users can create, edit, and delete their own application events.
- Users cannot read or mutate another user's application events.
- Permanent application deletion removes associated events.
- The experience is accessible, localized, responsive, and compatible with both form presentations.
- Shared contracts, API behavior, database behavior, and browser workflows have focused regression coverage.
