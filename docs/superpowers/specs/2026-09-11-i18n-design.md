# Internationalization Design

## Goal

Add a small, maintainable localization foundation for the React application. The initial interface supports English, Russian, and Ukrainian without changing the API contract, database schema, or user-entered application data.

## Approved scope

- Supported application locales are `en`, `ru`, and `uk`.
- The language selector appears in the shared header and visually uses the compact labels `EN`, `RU`, and `UK`.
- The selector is fully accessible: it has an accessible name, exposes the active locale, and each language control has an unambiguous accessible name in its own language.
- A selected language is stored only in the browser under a dedicated local-storage key. It is not written to the user record and does not follow a user between devices.
- When no explicit choice exists, the application resolves the browser language to a supported base language (`uk-UA` becomes `uk`; `ru-RU` becomes `ru`) and otherwise uses English.
- The document `lang` attribute updates whenever the active locale changes.
- Dates and other future locale-aware formatting use the resolved application locale rather than the browser default.
- All current frontend product copy, including accessible labels, client-side validation, loading and error copy, status labels, dialogs, empty states, and public pages, is translated.

## Technical design

Use `i18next` with `react-i18next`. React components receive translations through `useTranslation`; non-React code can use the initialized i18n instance only when necessary.

Translations live in `apps/web/src/i18n/locales/` as TypeScript modules, grouped by feature namespace:

- `common` for shared controls and status copy.
- `auth` for login, registration, and password recovery.
- `applications` for the board, forms, archive, and blacklist.
- `about` for the public About page.
- `errors` for client-presented API error codes and validation copy.

English is the default resource included in the initial application bundle. Russian and Ukrainian resource modules are loaded with dynamic imports only after the language is selected or detected. This keeps the initial bundle from carrying every translation while avoiding a translation HTTP service in the first version.

The locale dictionary shape is derived from English. Russian and Ukrainian dictionaries must satisfy the same key structure at compile time. Message values support interpolation and plural rules through i18next; JSX-rich strings use `Trans` only when a complete sentence must contain a React link or emphasis.

The i18n instance is the source of truth for language. Redux does not duplicate it. A small `LanguageSelector` owns user selection and calls the i18n language-change API. This follows the existing split between global presentation preferences and specialized framework state without introducing API or server state.

## Data, API, and server boundaries

- API paths, request/response fields, application statuses, error codes, and database values remain canonical and language-neutral.
- The browser maps stable API error codes to localized UI copy. It must not depend on human-readable server error messages for display.
- User-entered company names, positions, notes, locations, blacklist reasons, and application descriptions are never automatically translated.
- Current backend error text, SMTP email subjects/bodies, seed data, and documentation localization are out of scope. Localized transactional email is a later feature.
- `uk` is the BCP 47 language tag for Ukrainian. The compact visual selector label is `UK` by product decision; it is not a locale code for British English.

## Formatting and content rules

- Use `Intl.DateTimeFormat(activeLocale, options)` for all displayed dates. Move existing archive and blacklist date formatting behind a shared locale-aware formatter.
- Keep semantic dates in API/database ISO format; localization is presentation-only.
- Prefer stable semantic translation keys, such as `applications.status.saved` and `auth.login.submit`, rather than using English sentences as keys.
- Preserve dynamic values through interpolation rather than string concatenation. Plural-sensitive copy uses i18next plural forms.
- Do not translate technical identifiers, email addresses, URLs, job status API values, or test fixture keys.

## User experience and accessibility

- Language switching updates visible text without navigation or a full page reload.
- The selector remains available to guests and authenticated users, alongside the existing theme selector.
- Its controls must meet the project’s existing keyboard, focus-visible, pointer, and touch-target conventions.
- Switching locale updates `html[lang]`; all three supported languages are left-to-right.
- Translation changes must not alter form-control IDs, names, autocomplete values, routing, or accessible relationships.

## Error handling and fallback

- English is the configured fallback locale.
- An unsupported stored or browser locale is ignored and replaced with English.
- A malformed local-storage value cannot prevent startup.
- If a lazy locale module fails to load, retain the current rendered language, report the existing localized generic error pattern where appropriate, and allow retrying selection. Never leave the UI in a partially translated state.
- Development tests fail when a Russian or Ukrainian dictionary is missing an English key.

## Verification

- Add unit tests for locale resolution, local persistence, invalid-value fallback, and dictionary key completeness.
- Add focused component tests for selector labels and active state.
- Add a Playwright workflow that changes from English to Ukrainian and Russian, verifies visible application text and `html[lang]`, reloads, and verifies persistence.
- Verify date formatting uses the selected locale.
- Run lint, typecheck, unit tests, build, database seed, and Playwright E2E before completion.

## Out of scope

- Account-synced locale preferences.
- Locale-prefixed URLs, translated SEO metadata, or server-side rendering.
- Runtime translation editing, a translation-management service, machine translation, or remote translation loading.
- API, database, and email localization.
- Automatic translation of candidate data.
